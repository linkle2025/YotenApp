# 2. 要件（Scope）

[01_戦略.md](./01_戦略.md) の目的を実現するために、**何を作るか**と**何を作らないか**を決めます。

- 機能の要件（2.2）、コンテンツの要件（2.3）、非機能の要件（2.4）に分けて書きます。
- 各項目の「段階」は、[01_戦略.md の 1.8](./01_戦略.md#18-リリースの段階案) のリリース段階です。**段階1が新版の最初のリリース**です。
- 計算ルールの詳細は [付録A_鑑定ロジック仕様.md](./付録A_鑑定ロジック仕様.md)、現行の不具合は [付録B_現行システムの課題.md](./付録B_現行システムの課題.md) にあります。

## 2.2 機能の要件

### F-01 会員登録・ログイン・パスワード再設定（段階1）

Supabase Auth を使います。現行の Django 独自の仕組み（JWT、パスワード再設定メール）は引き継ぎません。

| # | 要件 |
|---|---|
| 1 | メールアドレスとパスワードで登録できる。登録時にメールの確認を行う |
| 2 | ログインはメールアドレスとパスワードで行う（現行のユーザー名でのログインはやめる。2026-11-09 決定）。表示名は別に持つ |
| 3 | パスワードを忘れたとき、登録したメールアドレスに再設定のリンクを送る。登録の有無がわからない応答にする |
| 4 | 登録画面の入力は最小限にする。生年月日などのプロフィールは、登録後に入力してもらう（現行は登録時に全部入力） |
| 5 | ログインが必要な画面に未ログインで来たら、ログイン後に元の画面へ戻す（現行は戻らない） |
| 6 | ログイン状態は、ブラウザを閉じても一定期間保つ。トークンの更新は Supabase に任せる（現行の更新処理の不具合をなくす） |
| 7 | パスワード変更では、現在のパスワードを確認する（現行は確認しない） |
| 8 | ログイン・登録・再設定に回数制限をかける（Supabase Auth の制限を使う） |
| 9 | 退会すると、本人のデータ（プロフィール・鑑定記録・判定の要点）を削除する（現行は無効にするだけで残る） |
| 10 | 段階4以降で、Google などの外部アカウントでのログインを検討する |

メールの送信元は yoten.app のメールサーバー（SMTP）を使います。Supabase Auth のメール設定に登録します。

### F-02 プロフィール（段階1）

| # | 要件 |
|---|---|
| 1 | 表示名、性別、生年月日、出生時刻（または時間不明）、出生地、居住地を登録・変更できる |
| 2 | プロフィールを登録すると、本人の鑑定記録を自動で作る。プロフィールを変えたら、本人の鑑定記録を作り直す（現行は履歴を全件読んで探し、性別を男性に固定して作っていた） |
| 3 | ホーム（ダッシュボード）から、本人の鑑定表へ1タップで行ける |
| 4 | 表示モード（経営者向け・保護者向け）を選べる（中身は F-14） |

### F-03 命式作成（段階1）

| # | 要件 |
|---|---|
| 1 | 入力：氏名（任意）、生年月日、出生時刻（または時間不明）、出生地、性別 |
| 2 | 生年月日は、存在しない日付（2月30日など）を入力できないようにする |
| 3 | 生年の範囲は、節入りデータのある 1901〜2040年。範囲外は理由を示して入力できないようにする |
| 4 | 出生地は47都道府県から選ぶ。補正には県庁所在地の値を使い、そのことを画面に示す（現行は都市名を選ばせていて、表記が不統一） |
| 5 | 海外で生まれた人の扱いは要確認（現行は非対応） |
| 6 | 作成したら、すぐ鑑定表へ移る |
| 7 | 時間不明のときは、時柱を使わない。**時刻補正もしない**（現行は0時として補正し、日柱が前日にずれる不具合がある） |
| 8 | 計算はサーバー側で行い、計算した結果を保存する。計算ロジックの版（例：`calc-1.0.0`）も保存し、後でロジックを直したときに再計算できるようにする |

### F-04 鑑定表（段階1）

| # | 要件 |
|---|---|
| 1 | 見出し：氏名（なければ「無題の鑑定」）、日干（画像と名前、比喩）、生年月日時、性別、出生地 |
| 2 | 命式の表：年柱・月柱・日柱・時柱の天干・地支・蔵干（本気・中気・余気）と通変星。時間不明の時柱は「—」 |
| 3 | 天干・通変星を押すと、その解説（F-08）を画面内で開く。キーボードでも操作できる |
| 4 | 五行バランス：日干の五行を上に置いた五角形の図、各五行の点数、該当する干支 |
| 5 | 身旺・身弱：比劫＋印と、食傷＋財＋官の比較。同点は「中和」と表記を統一する（現行は画面で「-」、スキル表で「中和」） |
| 6 | 格局、干合の注記 |
| 7 | 身旺・身弱・干合などの判定は、すべてサーバー側の計算に一本化する（現行は画面側とサーバー側で二重に計算している） |
| 8 | 鑑定スキル表（F-05）と判定の要点（F-06）を同じ画面に表示する |
| 9 | お気に入りの登録・解除、削除、印刷（F-15）ができる |
| 10 | スマートフォンでは縦一列、パソコンでは左右2列で読みやすく配置する（詳細は骨格） |

### F-05 鑑定スキル表（段階1）

| # | 要件 |
|---|---|
| 1 | 9つの能力（企画・知略・実行・体力・人望・統率・開拓・商才・管理）を0〜100点で示す |
| 2 | 7つの職種（将軍・軍師・教官・専門職・営業・現場L・総務）を点数と10段階のランク（S〜D）で示す |
| 3 | 能力・職種は点数の高い順に並べる |
| 4 | 各能力の点数の内訳（どの要素から何点か、どの解釈ルールで何点補正したか）を見られる |
| 5 | 時間不明のときは「参考値」と明示する |
| 6 | 計算式・重み・ランク帯は付録Aのとおり。現行と同じ結果を出すことをテストで保証する |
| 7 | 表示モードが「保護者向け」のとき、職種の見せ方を変えるかどうかは要確認（F-14） |

### F-06 判定の要点（AI解説）（段階1、順に流れる表示は段階2）

| # | 要件 |
|---|---|
| 1 | 鑑定スキル表の点数の根拠を、AI（Gemini）が日干を起点に文章で説明する。構成：要約、7職種ごとの説明、9能力ごとの説明、活かし方 |
| 2 | 生成はボタンを押したときに行う（自動では生成しない）。一度作った解説は保存し、次からはすぐ表示する |
| 3 | 点数や解釈ルールが変わって入力が変われば、古い解説は表示せず、作り直しを促す（現行と同じ） |
| 4 | **生成中は、書き上がった部分から順に表示する**（段階2）。段階1でも、進み具合がわかる表示にする（現行は約30秒、何も表示されない） |
| 5 | 1人あたり1日の生成回数に上限を設ける（現行は20回。設定で変えられる） |
| 6 | AI には、氏名・生年月日・出生時刻・出生地を送らない。干支・点数・解釈ルールだけを送る |
| 7 | AI の出力は形式（全職種がそろっているか、文字数など）を検証し、不備があれば1回だけ作り直す |
| 8 | 生成に失敗したら、理由に応じた文言（上限に達した、混み合っている、など）と再試行の手段を示す |
| 9 | 解説の下に、生成した AI のモデル名と生成日時、「AIによる解説で、断定ではない」旨を表示する |
| 10 | 有料枠のキーであることを確認する設定がオンのときだけ動く（現行と同じ安全装置） |

### F-07 鑑定記録の一覧（段階1）

| # | 要件 |
|---|---|
| 1 | 自分が作った鑑定記録の一覧。氏名、生年月日（時間不明なら時刻を出さない）、日干、作成日 |
| 2 | 氏名での検索、お気に入りでの絞り込み、並べ替え（作成日・氏名） |
| 3 | 一覧からお気に入りの切り替え、削除ができる。削除は取り消せる形（数秒間の「元に戻す」）にする |
| 4 | 件数が多くても速く表示する（ページ送りまたは続きを読み込む） |
| 5 | 記録が0件のときは、命式作成への案内を出す |

| 3 | 今の年齢に当たる大運・年運を強調する |

### F-10 奇門遁甲（段階1、管理者のみ）

| # | 要件 |

| 4 | 盤面：9つの宮に天盤干・地盤干・九星・八門・八神・格局・点数。八卦の象意、用途別（年運・疾病・男女・失せ物）の解説 |

### F-19 占者向け機能（段階4、要確認）

ロール「占者ユーザー」は現行では一般ユーザーと同じ扱いで、専用の機能がありません。想定される候補は次のとおりです。

- 相談者ごとのメモ、タグ、フォルダ分け
- 相談者に見せるための画面（余計な操作を隠した表示）
- 相談者への鑑定表の共有（期限つきのリンク）

### F-20 課金（段階4、要確認）

有料会員や回数課金を入れるかは未定です。入れる場合は、決済サービス（Stripe など）と特定商取引法の表記が必要です。

### F-21 正解データによる照合（段階0）

| # | 要件 |

## 2.4 非機能の要件

### 性能

| # | 要件 |
|---|---|
| 1 | 公開ページは、スマートフォンの4G回線で2秒以内に主要な内容を表示する（Core Web Vitals の LCP 2.5秒以内を目標） |
| 2 | 命式作成は、ボタンを押してから鑑定表が出るまで2秒以内 |
| 3 | 判定の要点は、生成開始から5秒以内に文章が出始める（段階2） |
| 4 | 十干・通変星のマスタは、画面を開くたびに全件を取りに行かない（現行は毎回取得している） |

### セキュリティ・個人情報

| # | 要件 |
|---|---|
| 1 | Supabase の全テーブルで RLS（行単位のアクセス制御）を有効にし、本人のデータは本人だけが読み書きできるようにする |
| 2 | 管理者の権限は、画面だけでなくデータベース側（RLS とサーバー処理）で確認する（現行は画面側の判定に頼る箇所がある） |
| 3 | 秘密の値（Gemini のキー、Supabase の service_role キー、SMTP のパスワード）は Vercel の環境変数に置き、ブラウザに渡さない |
| 4 | 通信はすべて HTTPS。セキュリティヘッダー（CSP を含む）を設定する（現行は CSP がない） |
| 5 | AI には氏名・生年月日・出生時刻・出生地を送らない。プライバシーポリシーで AI への送信を説明する |
| 6 | 退会したら本人のデータを削除する。管理者による削除も同じ |
| 7 | 依存パッケージの脆弱性を自動で検査する（GitHub の Dependabot など） |

### 可用性・運用

| # | 要件 |
|---|---|
| 1 | サーバーの管理（OS、Nginx、Docker）をなくす |
| 2 | `main`（または `master`）ブランチへのプッシュで本番に自動デプロイし、プルリクエストごとにプレビュー環境を作る |
| 3 | データベースは毎日自動でバックアップする（Supabase Pro） |
| 4 | データベースの変更（マイグレーション）は、ファイルで管理して自動で適用する |
| 5 | エラーを記録し、重大なエラーは通知する（Sentry など。要確認） |
| 6 | Vercel と Supabase は、どちらも東京リージョンに置く |

### 使いやすさ・アクセシビリティ

| # | 要件 |
|---|---|
| 1 | スマートフォン（幅 360px〜）を基準に設計し、タブレット・パソコンにも対応する |
| 2 | WCAG 2.2 の AA 相当を目標にする（文字と背景のコントラスト、キーボード操作、読み上げ） |

| # | 要件 |

## 2.5 作らないもの（範囲外）

| 項目 | 理由 |
|---|---|
| スマートフォンのアプリ（App Store・Google Play） | Web で十分に使えるようにする。必要ならホーム画面に追加できる形（PWA）を検討する |
| 既存会員とデータの移行 | 決定済み。会員に登録し直してもらう |

| 十二運、支合・冲、外格・破格、用神 | 現行でも未実装。要望があれば段階4以降で検討する |
