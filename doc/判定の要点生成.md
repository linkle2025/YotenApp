# 判定の要点（Gemini API による文章生成）α版

## 概要

鑑定スキル表（[鑑定スキル表.md](./鑑定スキル表.md)）の結果と命式データをもとに、Gemini API で「判定の要点」を生成する機能です。判定の要点とは、なぜその点数・ランクになったのかを説明する文章です。鑑定表ページでは、要約をスキル表の上に、職種ごと・能力ごとの解説を各項目の下に差し込んで表示します。

- **点数とランクは LLM に決めさせません。** `skill_sheet` の計算結果を正とし、LLM には根拠の説明文だけを書かせます。画面の「教官S：」のようなランク表記も、フロントが `skill_sheet` の値から付けます。
- **個人情報を扱うため、有料枠のキーでのみ使います。** 運用者が有料枠であることを確認し、`GEMINI_PAID_TIER_CONFIRMED=True` を設定するまでは、機能が起動しません。
- 氏名・ユーザー名・メールアドレス・生年月日・出生時刻・出生地は Gemini に送りません。命式の干支だけを送ります。
- 生成結果は DB（`SkillInsight`）に保存し、同じ入力なら再生成しません（コスト対策）。
- 生成するのはボタンを押したときだけです。ページを開いたときは保存済みの結果を読むだけです。
- 画面からの生成は最初の1回のみです（「再生成」ボタンは当面非表示）。API の `regenerate=true` は残しているので、ボタンを戻せば再開できます。

## 処理の流れ

```
[鑑定表ページ] 「判定の要点を生成」ボタン
   ↓ POST /api/fortune/history/<pk>/skill-insight/
[バックエンド] insight_service.generate_insight()
   1. 機能が有効か確認（有料枠確認・機能オン・APIキー）→ 無効なら 503
   2. 所有者チェック（他人の記録は 404）
   3. skill_sheet と命式から入力JSONを組み立てる（注記ファクトもここで検出）
   4. 入力JSON（context を含む）＋プロンプト版数＋モデル名の SHA-256 でキャッシュを確認
      → regenerate=false でキャッシュがあれば、それを返す（日次上限に数えない）
   5. 日次上限を確認 → 超えていれば 429
   6. Gemini を呼び出す（構造化出力）→ 応答を検証。不合格なら1回だけ再試行
      → それでも駄目、または API エラー・タイムアウトなら 502（保存しない）
   7. DB に保存して返す
[フロント] SkillReport コンポーネントが、要約・職種ごと・能力ごとの解説をスキル表に差し込んで表示
```

## 環境変数

`backend/config/settings.py` で `python-decouple` を使って読みます。本番は `.env.prod`（`docker-compose.prod.yml` 経由）、開発は `backend/.env` に書きます（例は `.env.prod.example`、`backend/.env.example`）。

| 環境変数 | 既定値 | 説明 |
|---|---|---|
| `GEMINI_API_KEY` | （空） | Google AI Studio の API キー。**課金を有効にしたプロジェクトのキー**を使う |
| `GEMINI_MODEL` | `gemini-3.6-flash` | 使うモデル |
| `GEMINI_PAID_TIER_CONFIRMED` | `False` | 有料枠のキーであることを運用者が確認したら `True` にする |
| `SKILL_INSIGHT_ENABLED` | `True` | 機能のオン・オフ |
| `SKILL_INSIGHT_DAILY_LIMIT` | `20` | 1ユーザーが1日に生成できる回数（キャッシュ命中は数えない） |
| `GEMINI_TIMEOUT_SECONDS` | `40` | API 呼び出し1回あたりのタイムアウト |

機能が有効になるのは、`GEMINI_PAID_TIER_CONFIRMED=True`、`SKILL_INSIGHT_ENABLED=True`、`GEMINI_API_KEY` 設定済みの3つがそろったときだけです。`GEMINI_PAID_TIER_CONFIRMED` が `True` でない場合は、初回の利用時に警告ログを1回出します（キーの値は出しません）。

### 有料枠に限る理由

Gemini API の無料枠では、入力内容が Google のサービス改善に使われる場合があります。命式は個人に結びつく情報なので、有料枠のキーだけを使います。API からキーが有料枠かどうかを確実に判定する方法はないため、運用者が確認したことを環境変数で明示する仕組みにしています。データの取り扱い条件は、運用を始めるときに Google の最新の利用規約で確認してください。

### モデルについて（2026-11-05 時点）

仕様書の既定値だった `gemini-2.5-flash` は非推奨になっており、2026年12月1日以降は `gemini-3.5-flash-lite` に自動で振り替えられます。そのため、既定値は公式に安定版と表示されている `gemini-3.6-flash` にしました。変更するときは `GEMINI_MODEL` を書き換えます。モデル名はキャッシュのハッシュに含まれるので、モデルを変えると次回は新しく生成されます。

### SDK と Python のバージョン

Google 公式の新 SDK `google-genai`（2.34.0 に固定）を使います。旧 `google-generativeai` は使いません。`google-genai` の最新版は Python 3.11 以上が必要なため、この機能の追加に合わせてバックエンドの Docker イメージを `python:3.12-slim` に上げました。あわせて、Python 3.12 に対応させるため `Django` を 4.2.30、`djangorestframework-simplejwt` を 5.3.1 に上げています。

## API

認証必須で、対象の計算記録の所有者だけが使えます（他人の記録は 404）。

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/fortune/history/<pk>/skill-insight/` | 最新の保存結果を返す。なければ `insight: null` |
| POST | `/api/fortune/history/<pk>/skill-insight/` | 生成する。body `{"regenerate": false, "context": null}` |

### レスポンス

```json
{
  "insight": {
    "summary": "…",
    "jobs": [{"key": "kyoukan", "text": "…"}],
    "abilities": [{"key": "kikaku", "text": "…"}],
    "advice": "…",
    "model_name": "gemini-3.6-flash",
    "prompt_version": "v1",
    "created_at": "2026-11-05T12:00:00+09:00",
    "is_cached": false
  },
  "available": true
}
```

- `available` は GET のときだけ返します。機能が無効なとき、フロントは生成ボタンの代わりに「現在、判定の要点は生成できません。」と表示します。
- `jobs` と `abilities` は、スキル表の表示順に並べ替えて保存します。

### エラー

| 状況 | ステータス | メッセージ |
|---|---|---|
| 機能オフ / キー未設定 / 有料枠未確認 | 503 | 現在、判定の要点は生成できません |
| 日次上限超過 | 429 | 本日の生成回数の上限に達しました |
| Gemini のエラー・タイムアウト・検証失敗 | 502 | 生成に失敗しました。時間をおいて再度お試しください |
| スキル表を算出できない古い記録 | 400 | この鑑定表では判定の要点を生成できません |
| body の形式が不正（regenerate・context） | 400 | 項目ごとのメッセージ |

## Gemini に渡す入力JSON

`insight_service.build_insight_input()` で組み立てます。

| 項目 | 内容 |
|---|---|
| `day_stem` | 日干と、その比喩（十干マスタの `element_type`。例：田畑） |
| `pillars` | 年・月・日・時柱の干支、天干の通変星（日柱は「日干」）、蔵干（本気・中気・余気）と通変星。時間不明なら `hour` は `null` |
| `hour_unknown` | 時間不明フラグ |
| `element_groups` / `star_points` | 五行グループ点数 E、通変星点数 P |
| `strength` / `kakukyoku` | 身旺身弱、格局 |
| `abilities` | 能力ごとの点数と `breakdown`（算出式の各項と値） |
| `jobs` | 職種ごとの点数・ランクと `weights`（能力名: 重み） |
| `notable_facts` | 注記ファクト（下記） |
| `context` | 本人コンテキスト（α版では常に `null`） |

## 注記ファクト

LLM が命式にない概念を作り出さないよう、伝統的な注目点はコード側で検出して事実として渡します。点数には影響させません。

| ID | 条件 | 文言の例 |
|---|---|---|
| `shokan_kenkan` | 天干（日干を除く）に傷官と、正官または偏官が両方ある | 傷官見官：時干の傷官（庚）と年干の偏官（乙）が天干に並ぶ |
| `in_dominant` | 身旺で、E印 が5グループ中最大 | 印が最も強い身旺（印 30）：学びが厚い一方、考えすぎて出力が遅れやすい |
| `zai_scarce` | E財 < 5 | 財星がほぼない（財 2.5） |
| `kan_scarce` | E官 < 5 | 官星がほぼない（官 0） |
| `shokushou_strong` | E食傷 が上位2位以内かつ 20以上 | 食傷が強い（食傷 25）：表現・制作の出口が太い |

時間不明の場合、時干は判定に使いません。

### 注記ファクトの追加方法

1. `skill_facts.py` に検出関数を追加します。`FactContext` を受け取り、該当すれば文言（具体的な干・柱・点数を埋め込んだ文字列）を、しなければ `None` を返します。
2. `FACT_RULES` に `('ID', 関数)` を追加します。並び順がそのまま渡す順番になります。
3. `tests/test_skill_insight.py` の `NotableFactsRuleTests` にテストを追加します。

注記ファクトが変わると入力JSONも変わるので、次回は自動で新しく生成されます。

## プロンプト

`backend/apps/fortune/prompts/skill_insight_v1.md` に置いています。コード内には書いていません。ファイルは次の3つのセクションに分かれています。

| セクション | 内容 |
|---|---|
| `system` | システム指示（点数を変えない、入力にない概念を持ち出さない、低い項目にも補い方を添える、など）と良い出力の例 |
| `user` | ユーザー入力のテンプレート。`{{input_json}}` と `{{context_block}}` を置き換える |
| `context` | 本人コンテキストがあるときだけ `{{context_block}}` に差し込む「本人について」欄 |

出力は Gemini の構造化出力（`response_mime_type="application/json"` と `response_schema`）で、`summary` / `jobs` / `abilities` / `advice` の形にそろえます。職種と能力の `key` は列挙型で指定しています。

仕様書 §1 の例文は、点数・ランクを変えないという方針に合わせて少し書き換えて、良い出力の例として入れています。

- 「少数精鋭なら B まで上がります」のようにランクが変わることを示す表現は、「力を発揮しやすくなります」に変えました。
- 「教室やサポート校の開校」「本人の実感とも整合します」は、本人コンテキストがある場合の例に分けました。

### 版数の上げ方

1. `prompts/skill_insight_v2.md` のように、新しい版のファイルを作ります（v1 は残します）。
2. `insight_service.py` の `PROMPT_VERSION` を `'v2'` にします。
3. 版数はキャッシュのハッシュと `SkillInsight.prompt_version` に入ります。版数を上げると、次回の生成から新しいプロンプトが使われます。古い結果は、GET では新しい結果ができるまで表示されます。

## 応答の検証

`validate_content()` で次を確認します。不合格なら1回だけ再試行し、それでも駄目なら 502 を返します（保存しません）。

- JSON として解釈でき、`summary` / `jobs` / `abilities` / `advice` がそろっていること
- `jobs` の key が7職種すべてそろい、余分な key や重複がないこと
- `abilities` は任意。key は9能力のいずれかで、重複がないこと
- どの text も空でなく、400字以内であること

## 本人コンテキスト（将来対応）

α版では入力 UI を作っていませんが、API は次の形の `context` を受け取れます。

```json
{"age": 41, "occupation": "教室経営", "position": "創業者", "industry": "教育・IT", "note": "自社の参謀役ができていないと感じている"}
```

- 受け付ける項目は `age`（0〜130の整数）、`occupation` / `position` / `industry` / `note`（各500字以内の文字列）だけです。それ以外の項目は 400 エラーにします。
- context を渡した場合だけ、プロンプトに「本人について」欄が入ります。
- context が変わるとハッシュも変わり、別のキャッシュになります。使った context は `SkillInsight.context` に保存します。
- 次のフェーズでは、鑑定表ページに入力フォームを追加し、保存先（ユーザー単位か計算記録単位か）を決めます。

## 管理画面

Django 管理画面の「判定の要点」で、生成履歴（計算記録、生成者、モデル、プロンプト版数、入力・出力トークン数、生成内容）を確認できます。入力トークン数・出力トークン数は、再試行した場合2回分の合計です。

## 本番運用の注意

- Gemini の呼び出しは1回あたり最大40秒、再試行を含めると最大80秒ほどかかります。そのため `nginx-proxy.conf` で判定の要点の URL だけ `proxy_read_timeout` を120秒にしています。サーバーの nginx 設定にも反映が必要です（[VPSデプロイガイド.md](./VPSデプロイガイド.md)）。
- APIキーはログ・エラーメッセージ・レスポンスに出しません。Gemini のエラーをログに残すときは、キーの文字列を伏せ字にします。

### 実キーでの手動確認（1回だけ）

1. `backend/.env` に有料枠のキーを設定し、`GEMINI_PAID_TIER_CONFIRMED=True` にします。
2. `docker-compose restart backend` で再起動します。
3. 石川さんの鑑定表で「判定の要点を生成」を押します。
4. 仕様書 §1 の例と同じくらいの内容になっているか、入力にない概念（十二運・天中殺・干合など）を持ち出していないかを目で確認します。
